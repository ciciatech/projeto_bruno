# T11 · Adotar shadcn/ui no frontend

## Decisão: WAITING (não bloqueia, mas não vale executar agora)

### Análise

shadcn/ui é mais útil quando o app tem:
- **Formulários** (Input, Form, Label, Select com validação)
- **Diálogos/modais** (Dialog, Sheet, Popover)
- **Comandos** (Command palette, Combobox)
- **Tabelas com sort/paginação** (DataTable do shadcn)

Estado atual do `frontend/src/`:
- 0 formulários
- 0 modais/diálogos
- 0 popovers
- 1 tabela (snapshot 14 regiões), simples, ordenada server-side
- 1 botão de toggle tema, 1 botão de "limpar filtros", botões de FilterBar
  (segmentados, com lógica visual específica)

Os componentes customizados que já existem (Panel, KPI, Sparkline,
Choropleth14CE, EditorialNote) **não têm equivalente direto** no shadcn —
são específicos do design Prisma Regional (paleta âmbar editorial,
tipografia serif/mono).

### Risco de adotar agora

shadcn/ui injeta seu próprio sistema de tokens CSS (`--background`,
`--foreground`, `--primary`, etc.) via `index.css`. Integrar com o
`tokens.css` atual (paleta âmbar editorial) exige:

1. Reescrever o `:root` do `lib/tokens.css` para usar a convenção shadcn
   (HSL channels), mantendo as cores âmbar.
2. Refatorar componentes existentes que leem `var(--ink-1)` etc. para
   trabalhar com a nova convenção.
3. Validar tema dark mode em todos os componentes.

Esse é um refator de ~half-day, não de 45min. E o ganho é **zero**
até existir um caso de uso real (form/dialog/popover) que justifique
o componente shadcn.

### Plano alternativo

Manter T11 em WAITING. Re-abrir quando aparecer **um** dos triggers:

- Tela 4 (Causal) precisar de `Dialog` para mostrar detalhes da regressão.
- FilterBar precisar de `Combobox` (ex: filtro por região com busca).
- Cadastro/edição de cenários (forma) — não previsto.

Quando trigger surgir, executar:

```bash
cd frontend
npx shadcn@latest init    # cria components.json, atualiza index.css
npx shadcn@latest add dialog  # ou button, table, etc.
```

E fazer migração gradual (não reescrever tudo de uma vez).
